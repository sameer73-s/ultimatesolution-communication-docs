# البرومبت الرئيسي لـ Manus
## مشروع: منصة التواصل المؤسسي – Ultimate Solution

**تعليمات الاستخدام:** أرسل هذا البرومبت كاملاً لـ Manus في بداية المشروع. بعدها، في كل مرة تريد بدء مرحلة جديدة، أرسل فقط رسالة قصيرة تقول "ابدأ بالمرحلة رقم X المذكورة في البرومبت الرئيسي" بعد إرفاق ملف الدليل المعماري (Architecture Guideline). **لا تنتقل لمرحلة جديدة قبل مراجعتنا واعتمادنا للمرحلة الحالية.**

---

## السياق (Context)

أنت تعمل على بناء منصة تواصل مؤسسي داخلية لشركة **Ultimate Solution**، بديل داخلي لـ Microsoft Teams، بميزة تنافسية أساسية هي **الذكاء الاصطناعي لتلخيص وإدارة الاجتماعات**. المشروع يُبنى بالكامل من الصفر باستخدام **ASP.NET Core** للـ Backend و**Flutter** للـ Frontend.

يوجد مستند مرفق باسم **"Architecture Guideline"** يحدد كل التقنيات، البنية المعمارية، وقواعد الجودة الإلزامية. **يجب الالتزام الحرفي بهذا المستند في كل مرحلة دون استثناء.** أي انحراف عنه يتطلب موافقة صريحة مسبقة مني.

العمل يتم **على مراحل متسلسلة صارمة**. لا تنتقل للمرحلة التالية إلا بعد استلام تأكيد صريح مني باعتماد المرحلة الحالية.

---

## المرحلة 0: البحث والتحليل + العرض التقديمي (Business Discovery)

**الهدف:** فهم السوق والمنافسين، وإنتاج عرض تقديمي يُعرض على إدارة الشركة لإقناعهم بجدوى المشروع.

**المطلوب:**
1. تحليل 4 منصات على الأقل: Microsoft Teams، Slack، Zoom، Rocket.Chat (أو Mattermost) من ناحية:
   - الميزات الأساسية والمتقدمة
   - نموذج الاستخدام والتسعير (إن وجد)
   - نقاط الضعف/الشكاوى الشائعة من المستخدمين (يمكن البحث عنها)
2. تحديد "الفجوة" (Gap) التي يسدها مشروعنا، بالتركيز على:
   - أن المنصة داخلية ومخصصة لشركة Ultimate Solution (لا اشتراكات خارجية)
   - ميزة الذكاء الاصطناعي لتلخيص الاجتماعات واستخراج المهام تلقائياً (ميزة غير متوفرة بنفس الجودة في الحلول المجانية/الرخيصة)
   - إمكانية التخصيص الكامل لاحقاً (بريد إلكتروني مدمج، تكاملات داخلية)
3. إنتاج **عرض تقديمي (PowerPoint)** احترافي يتضمن:
   - المشكلة الحالية (الاعتماد على أدوات متعددة ومنفصلة: واتساب + زووم/تيمز)
   - الحل المقترح
   - الميزة التنافسية (AI)
   - خارطة الطريق (Roadmap) المختصرة
   - التكلفة التقديرية مقابل التوفير المتوقع (استخدم افتراضات معقولة موضحة كـ "تقديرية")

**التسليم المتوقع:** ملف PowerPoint واحد جاهز للعرض، بدون هوية بصرية نهائية بعد (سيُطبَّق التصميم لاحقاً عند استلام الهوية).

## المرحلة 1: التصميم الهيكلي (System Design)

**الهدف:** بناء المخططات التقنية الأساسية قبل أي كتابة كود.

**المطلوب:**
1. **مخطط قاعدة البيانات (ERD):** يغطي الكيانات الأساسية: المستخدمون، الأدوار، القنوات/المجموعات، الرسائل، الاجتماعات، تسجيلات الاجتماعات، الملخصات، المهام المستخرجة (Action Items)، الإشعارات.
2. **مخطط المعمارية العام (Architecture Diagram):** يوضح تدفق البيانات بين: Flutter App ↔ ASP.NET API ↔ SignalR Hubs ↔ SQL Server ↔ خدمة الذكاء الاصطناعي الخارجية.
3. **Sequence Diagrams** لسيناريوهين حرجين:
   - إرسال واستقبال رسالة فورية
   - عقد اجتماع → تسجيله → تفريغه → تلخيصه → استخراج المهام منه
4. **تصميم أولي لعقود الـ API (API Contracts)** الأساسية (بدون تنفيذ بعد) — فقط الـ Endpoints المتوقعة مع شكل الطلب/الاستجابة، متوافقة مع القسم 6 من دليل المعمارية.

**التسليم المتوقع:** ملفات مخططات (يفضّل بصيغة قابلة للتعديل مثل draw.io/Mermaid) + مستند نصي يشرح كل مخطط.

## المرحلة 2: إدارة المشروع (Excel للفريق)

**الهدف:** أداة متابعة يستخدمها الفريق طوال المشروع.

**المطلوب:** ملف Excel يحتوي على:
1. ورقة **WBS** (تقسيم كل مرحلة إلى مهام فرعية قابلة للقياس)
2. ورقة **Timeline** (تقديري، بصيغة Gantt بسيطة باستخدام تنسيق شرطي)
3. ورقة **توزيع المهام** (عمود لاسم المسؤول — يُترك فارغاً للتعبئة اللاحقة)
4. ورقة **حالة المهام** (Not Started / In Progress / Blocked / Done) مع تنسيق شرطي بالألوان
5. ورقة **Risks & Notes** لتسجيل أي عوائق أو ملاحظات أثناء التنفيذ

**التسليم المتوقع:** ملف `.xlsx` واحد منظم بعدة أوراق (Sheets) مترابطة.

## المرحلة 3: بناء الـ Backend (ASP.NET Core) — تُنفَّذ كخطوات فرعية متسلسلة

> **إلزامي:** الالتزام الحرفي بالبنية المعمارية الموضحة في القسم 3 من "Architecture Guideline" (Clean Architecture: Domain / Application / Infrastructure / API، CQRS مع MediatR، Repository Pattern).

### 3.1 الأساس (Foundation)
- إعداد الـ Solution بالبنية الأربعة الطبقات
- إعداد DbContext وأول Migration
- Middleware موحّد للأخطاء + استجابة API موحّدة (حسب القسم 6)

### 3.2 المصادقة والصلاحيات (Auth)
- ASP.NET Identity + JWT
- الأدوار: Admin / Manager / Employee
- Endpoints: تسجيل، دخول، تجديد التوكن، إدارة المستخدمين (للمدير)

### 3.3 خدمة الشات والحضور (Chat + Presence)
- SignalR Hub للرسائل الفورية
- حالة الاتصال (Online/Offline/Away)
- قنوات فردية وجماعية، أرشفة، بحث أساسي

### 3.4 خدمة الاجتماعات (Meetings)
- جدولة اجتماع (وقت، مشاركون، أجندة)
- بدء/إنهاء اجتماع، ربط بخدمة الوسائط (WebRTC/Jitsi حسب ما تقرر في المرحلة 1)
- تسجيل الاجتماع (تخزين الملف الصوتي/المرئي)

### 3.5 خدمة الذكاء الاصطناعي (AI Meeting Intelligence)
- استدعاء خدمة تفريغ صوتي خارجية (Whisper/Azure Speech)
- استدعاء Claude API لتلخيص النص المفرّغ واستخراج نقاط القرار والمهام (Action Items) بصيغة منظمة (JSON)
- تخزين الملخص والمهام المستخرجة مرتبطة بالاجتماع

### 3.6 الإشعارات (Notifications)
- إشعارات داخل التطبيق عبر SignalR
- نقطة تمديد لاحقة لإشعارات Push/Email

**بعد كل خطوة فرعية (3.1 إلى 3.6):** توقف وسلّم الكود مع توثيق مختصر (README لكل Feature) لمراجعتنا قبل المتابعة للخطوة التالية.

## المرحلة 4: بناء الـ Frontend (Flutter)

> **إلزامي:** الالتزام الحرفي بالبنية الموضحة في القسم 4 من "Architecture Guideline" (Clean Architecture + Bloc + Feature-based، عزل تام بين الطبقات).

تُبنى الـ Features بنفس تسلسل الـ Backend، وبنفس المبدأ (توقف بعد كل Feature للمراجعة):

1. **Core Setup:** `core/` كامل (theme placeholder، network client، error handling، routing، DI عبر get_it)
2. **Auth Feature**
3. **Chat Feature**
4. **Meetings Feature**
5. **AI Summary Feature** (عرض الملخصات والمهام المستخرجة)
6. **Notifications Feature**

**لكل Feature، التسليم يجب أن يتضمن:**
- الطبقات الثلاث كاملة (data/domain/presentation) مطابقة تماماً للقالب في القسم 4
- Bloc منفصل بأسماء صريحة
- ربط فعلي بالـ Endpoints المطابقة من الـ Backend (وليس بيانات وهمية mock إلا في مرحلة الاختبار الأولي إن لزم، مع توضيح ذلك صراحة)
- ملاحظة بأي نقطة غير واضحة تحتاج قرار منا قبل الافتراض

**ملاحظة حاسمة:** سيقوم المطور المسؤول من جانبنا باختبار كل Feature فعلياً بعد التسليم وإرسال أي ملاحظات/أخطاء لتصحيحها قبل اعتماد الانتقال للـ Feature التالية.

## المرحلة 5: استخراج وتطبيق الهوية البصرية (Branding)

### 5.1 استخراج الهوية البصرية (يُنفَّذ الآن، مبكراً، بالتوازي مع أي مرحلة أخرى)

**الهدف:** استخراج الهوية البصرية الرسمية لشركة Ultimate Solution من موقعيها الرسميين، بدلاً من انتظار تسليمها يدوياً.

**المصادر:**
- https://ultimatesolutionsportal.com/
- https://www.ultimate-erp.com/

**المطلوب تحديداً:**
1. **الشعار (Logo):** تنزيل أعلى دقة متاحة من الموقعين (لاحظ أن كل موقع يستخدم نسخة شعار مختلفة قليلاً — قارن بينهما وحدد الأحدث/الأنسب، أو اعرض الخيارين علينا للاختيار). احفظها بصيغ PNG شفافة الخلفية، وحوّل نسخة إلى SVG إن أمكن.
2. **الألوان:** افحص أوراق الأنماط (CSS) الفعلية للموقعين (وليس فقط الصور) لاستخراج:
   - اللون الأساسي (Primary) المستخدم في الهيدر/الأزرار الرئيسية
   - اللون الثانوي/المميز (Accent)
   - ألوان النصوص والخلفيات القياسية
   - أرقام Hex دقيقة لكل لون (وليس تقديراً بصرياً)
3. **الخط (Typography):** حدد اسم عائلة الخط (Font Family) المستخدمة فعلياً في CSS الموقعين (عربي وإنجليزي إن اختلفا)، وتحقق هل هو خط مفتوح المصدر متاح (Google Fonts مثلاً) يمكن استخدامه مباشرة في Flutter وASP.NET.
4. **ملاحظة الفروقات:** إذا وُجد تعارض بين هوية الموقعين (شعار مختلف، ألوان مختلفة)، وثّق الفروقات بوضوح واقترح توصية بدلاً من افتراض أحدهما تلقائياً.

**التسليم المتوقع:** مستند مختصر "Brand Extraction Report" يحتوي:
- ملفات الشعار المستخرجة
- جدول الألوان مع أكواد Hex
- اسم الخط ورابط تحميله إن كان مفتوحاً
- التوصية النهائية في حال وجود تعارض

**بعد اعتمادنا لهذا التقرير**، يُحدَّث قسم 5 في "Architecture Guideline" بالقيم النهائية، وتصبح مصدر الحقيقة الوحيد للتصميم بقية المشروع.

### 5.2 تطبيق الهوية (يُنفَّذ بعد اعتماد 5.1)

عند اعتماد الهوية المستخرجة، تُطبَّق حصراً عبر:
- تحديث `core/theme/` في Flutter (لا تعديل مباشر في الـ Widgets)
- إعادة تصميم العرض التقديمي من المرحلة 0 بالهوية النهائية
- تنسيق ملف الـ Excel (رأسيات، ألوان الحالة) بما يتماشى مع الهوية

## تذكير عام لكل مرحلة

- التزم حرفياً بمستند "Architecture Guideline" المرفق
- لا تفترض قراراً تقنياً غير موثّق — اسأل بدلاً من الافتراض
- سلّم كل مرحلة/خطوة فرعية بشكل منفصل مع توثيق مختصر لما تم إنجازه ولماذا
- انتظر التأكيد الصريح "معتمد، انتقل للمرحلة التالية" قبل البدء بأي مرحلة جديدة
